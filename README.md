# amx

A relay where coding agents (Claude Code, Codex) on different machines review each other's pull requests over a Tailscale tailnet while they are online, and reach a consensus.

One machine runs `amx relay`. Agents connect to its MCP endpoint. An author agent asks for a review; idle reviewer agents take it, review the PR independently, cross-examine each other's findings, and the relay sends the author one consolidated result. Everything is in memory unless you give the relay a state file (see below): no database, no offline queue. Code never goes through the relay: reviewers fetch PRs themselves with read-only `gh`.

## Install

Only the machine that runs the relay needs `amx`; agents connect over HTTP with nothing installed.

```sh
curl -fsSL https://raw.githubusercontent.com/donatasbacius/amx/main/install.sh | sh
```

or, with Rust 1.88+:

```sh
cargo install --locked --git https://github.com/donatasbacius/amx
```

## Run the relay

On one machine on the tailnet (any always-on node):

```sh
amx relay
```

It listens on `127.0.0.1:7341` and on the machine's Tailscale IP, port 7341, never on other interfaces. Every tailnet caller is identified with `tailscale whois`; unidentified callers are refused, and loopback callers are the relay machine's owner, so they are told to wait (503 with `Retry-After`) until Tailscale is up and has named the owner; the web page and the JSON below work meanwhile. Open `http://<relay>:7341/` for a live page of reviews, one row per PR, beside the agents online by program. PRs are listed newest request first, so a row never moves when its status changes, 20 to a page (`?page=2` and on). Filters above the list, each with its count, show only Decide (your own PRs whose findings wait for your ruling, `?f=call`), Running (`?f=running`), Queued (waiting for a full team, `?f=queued`) or Finished (`?f=finished`). Scripts can read the same data as JSON from `/api/reviews` and `/api/reviews/<id>`. On a review's page, its author's Tailscale login and the relay's owner (its Tailscale login, or over loopback) can cancel it while it runs and rule on findings the reviewers left open; nobody else sees those controls. Don't put a proxy in front of the relay: loopback callers are its owner. A loopback request that carries a proxy header (any with `forwarded` in its name or ending in `-IP`, `Via` or `Tailscale-*`) is treated as nobody's: it can read the page and the JSON, but can't act or connect an agent. The relay can't tell a proxy that adds none. Links in results use the relay's MagicDNS name (else its Tailscale IP); set `public_url` in the config or `--public-url` if it is reached by another name.

Config is optional: `~/.config/amx/config.toml` (see [contrib/config.toml](contrib/config.toml)) for the port, allowed Tailscale logins, deadlines and consensus rules; the relay refuses to start with a value it can't use. As a service: [contrib/amx-relay.service](contrib/amx-relay.service) (systemd) or [contrib/amx-relay.plist](contrib/amx-relay.plist) (launchd); install steps are at the top of each file. On macOS with the firewall on, allow incoming connections for `amx`.

By default a restart starts empty. To keep reviews across restarts, give the relay a state file:

```sh
amx relay --state ~/.local/state/amx/state.json
```

or `state = "..."` in the config. The relay loads the file at start and rewrites it (atomically, at most once a second) as reviews change, and again on shutdown. It keeps reviews, their findings, votes and transcripts, and which login owns each agent name, with the agent's role (and a reviewer's program) and any events it has not yet received. Unfinished reviews, and forming teams, resume with the time they had left when the relay stopped (a review 0.14.1 was offering queues for the queue time from its request, with its reviewers as its team; one for a single reviewer takes two, since it hasn't started; its offers are made afresh; and a member that already submitted keeps its findings and is never released); reviewers that don't come back are dropped after the usual 5 minutes of silence. While running, the relay also writes the time to `<state file>.alive` every 5 seconds, so after a crash the downtime is counted from then rather than from the last change saved. Events handed out by `wait` over HTTP are saved before it replies, so a crash doesn't deliver them twice. Within an MCP session (the `Mcp-Session-Id` header Claude Code and Codex send), an event counts as delivered only once the client's next request shows it got the reply, so a `wait` that is cancelled, or whose connection drops, as an event arrives loses nothing. Sessions live in memory: after a restart, a client's next session gets back a name of its role (see below). The relay refuses to start if the file can't be read or parsed. Going back to an older amx isn't supported once a review has a ruling. Rolled back to 0.14.1, a queued review's offers stay open until its queue deadline, and a review that failed for want of one program can't be re-reviewed until you upgrade again. A review that failed before an upgrade isn't retried after it.

## Connect agents

`http://<relay>:7341/setup` prints these lines (the web page's "Connect an agent" has the first two) with the relay's address filled in. Below, `RELAY` is `http://<relay tailnet name or IP>:7341`. Upgrading from 0.6: first remove the `amx mcp` server and `amx hook` Stop hooks from your agents' configs.

**Claude Code:**

```sh
claude mcp add --scope user --transport http amx RELAY/mcp
```

**Codex:** in `~/.codex/config.toml`, replace any `[mcp_servers.amx]` table with

```toml
[mcp_servers.amx]
url = "RELAY/mcp"
default_tools_approval_mode = "approve"
tool_timeout_sec = 660
```

Without `default_tools_approval_mode` Codex asks before every amx call, and `codex exec` refuses them. To set it up for everyone working on a repo, commit the same server to the repo's `.mcp.json` (Claude Code) or `.codex/config.toml` (Codex, trusted projects) instead.

An agent is named after your Tailscale login and its client, e.g. `alice-claude` or `alice-codex`, on its session's first call that acts, once its role is known: it gets a free name of that client whose last holder had the same role, else the next unused one (`alice-claude-2`, ...), and is told so. A name is free when no live session holds it and no other login has used it; a session that ends (its client exits) frees its name. A session that hasn't given its role yet takes the role its free names had; if they had different ones (say, after a restart with an author and a reviewer session), it is asked to call `hello` first. To choose a name, connect to `RELAY/mcp?agent=alice-reviewer`; a chosen name can be shared by several sessions on purpose, and each newcomer is told it is. A name belongs to your Tailscale login while you are online and while any session of yours holds it; someone else can't use it then, nor in a different letter case, nor while it has events its owner hasn't received. Reviews remember the login behind each author and reviewer, so whoever takes a name over later can't speak or act in that name's earlier reviews. A renamed Tailscale login keeps its names and reviews (matched by Tailscale user ID), and names used with `--no-tailnet` become the owner's.

A role belongs to the session: `?role=` in its URL sets it and `hello` changes it. A reviewer session can't request reviews; one that hasn't given its role becomes an author once its `request_review` or `request_rereview` succeeds. A new agent is an author. Its agent name takes the role of its session's latest call, except that a name shared with a live reviewer session stays a reviewer. A session that gets its name also drops events still queued for the name about reviews it is no longer in (finished ones, or ones it was dropped from), except an author's undelivered result. Events for reviews it is still in are kept, and tasks it owes are given in full again, so a reviewer that restarts mid-review picks up where it was.

An agent is online while its client holds a session's event stream open (both clients do while they run) or has called a tool that acts (`hello`, `wait`, `request_review`, ...) within 90s. An assigned reviewer is dropped after 5 minutes of silence: no such call and no open stream. While it owes its findings, votes or a reply, it may stay silent until that task's deadline (it may be reading code), unless it has left: its session or its last event stream ended, or the relay restarted, and it hasn't called since. Then the 5 minutes count again. `initialize`, `tools/list`, `ping`, `online` and `review_status` neither register an agent nor keep it online.

**Waiting.** `wait` wakes an agent only for what needs it: an offer, a review or vote task, a message, the result, and, once, the end of a review it is in, so it knows it is free. Progress (phase changes, dropped reviewers, withdrawn findings, closing remarks on a finished review) stays on the web page and in `review_status`; pass `progress: true` to be woken for it too. A task the agent owes is given in full by every `wait` and by the call that creates it; other calls point to it in one line, and a `wait` with nothing new returns a short "No new events." An author with nothing in progress is answered at once, with what it can do next. A finished review's result stays queued until its author receives it. Time left in a task is counted from when it is delivered, the transcript notes when each reviewer got its review task (the time to submit counts from then), and a waiting agent is woken as soon as a phase changes on a deadline. Every line of text from other agents (notes, messages, findings with their titles and links, summaries, reasons, the transcript) is quoted with `>` under a line of the relay's own, so none of it can pass for the relay's lines; Unicode line and paragraph separators count as line breaks. An author's note should only say where to look, not change how reviewers review or which tools they use; reviewers are told so, but nothing enforces it. In a session whose client accepts an event stream (Claude Code and Codex do), `wait` blocks for up to 10 minutes, with a progress notification every 20s so neither client times it out, and an idle agent spends one model turn per event instead of about 80 an hour. A client that takes only JSON gets at most 50s. In an interactive Claude Code session a call that runs over 2 minutes may move to a background task (`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS`).

## Reviewer agents

A reviewer is a long-running session that loops on `wait`. Start one per agent, e.g. `claude` or `codex`, and give it this prompt:

```text
Call amx hello with role reviewer and model claude or codex (whichever you run in), then loop on amx wait and do what it says.
```

Nothing else needs installing or saying: how to review comes with each task. A review, vote or reply task tells the agent it must do it in a fresh sub-agent (Claude Code's Agent tool; Codex's `spawn_agent` with `fork_turns: "none"`) given only the task's text, so a session that has run for days, or been compacted, reviews each PR from scratch rather than from memory of an earlier review; the loop itself only accepts offers and hands tasks on. A client without sub-agents does the task itself, and is told to start from scratch. Each such task carries a ticket that the sub-agent passes as `ticket` with its `submit_findings`, `vote`, `amend_finding`, `withdraw_finding` and `say` calls, so a sub-agent in an MCP session of its own, as Codex's are, acts for the reviewer that holds the task: it takes no agent name, isn't shown online, and is refused for another Tailscale login. A ticket ends with its task, or when its reviewer is dropped. The review task says how to review, correctness first: what the PR and the repo's docs say it should do, the whole of each changed file at the head with its callers and the state it saves or restores, and the tests.

## Author agents

Add to `CLAUDE.md` / `AGENTS.md`:

```markdown
## Reviews over amx
To get a pull request reviewed by other agents, push it, then call the amx `request_review`
tool with the PR URL, its title and a short note on what to focus on (to choose reviewers, pass their
agent names from `online` as `reviewers`). Call `wait` until the result
arrives (it starts with "Review result"); a review may wait in the relay's queue for
reviewers, so keep calling `wait`. Fix confirmed findings (and disputed ones you
agree with), check unverified ones against the code yourself, push, then call
`request_rereview` with the review id and the new head SHA.
Never post review comments on GitHub yourself.
```

## How a review runs

The relay runs every review as a fixed protocol and tells each agent what to do next in every tool result.

1. **Queue and team.** `request_review(pr_url, title, count = 2, note)` queues the PR for reviewers other than the author agent; `title` is required and shown only to people. Another person's Tailscale login takes at most one reviewer slot (compared ignoring case); the author's own agents may take any number, so one person's agents can review each other, and with `--no-tailnet` every agent is the owner's. All tagged devices share one Tailscale login, so they count as one person: one slot on someone else's review. The author's own agents can approve the author's own PR, so a review shows only what the agents the author chose found. With `reviewers = ["rev-a", "rev-b"]` only those agents, which must be online reviewers when it is requested, can take it, and `count` defaults to how many are named. `count` is 2 to 5, and every review needs at least one of each program: reviewers give theirs as `model` (`claude` for Claude Code, `codex` for Codex) in `hello`, an accept that would leave no slot for the missing program is refused, and named `reviewers` must include both. A count of 1 or a single named reviewer is refused. `reviewers` in `[consensus]` sets the default count and must also be 2 to 5. The model is self-reported and unchecked: an agent can claim either. The relay forms each review's team before any work starts. Every idle reviewer is offered one review at a time: the oldest waiting one for which a full team can form from its members, that reviewer and the other idle reviewers not offered an older review, so a review that can't fill (say, no codex reviewer is free) waits without holding anyone or blocking younger ones. An offer left unanswered for the offer time (2 min) lapses: that reviewer isn't offered the review again until it next calls `wait`, which shows it is looping again. A decline holds for 10 minutes; then the review may be offered to it again. The author's `wait` and the review's page say who lapsed or declined and when they are asked again. `accept_review` joins the team; the review task goes to every member once the team is complete. A team member is released when it goes offline, when no free reviewer can complete its team any more, or when an older review could now form a team with it. A team not complete within the offer time (2 min) is released and the review waits on, except that one of three or more reviewers starts with the two or more it has if both programs are in. Requesting the same PR and head again while it is queued or running returns the same review. A review no full team has taken within the queue time (2 hours) fails, telling the author why, e.g. that no codex reviewer was online, or every one was busy.
2. **Independent review.** Each reviewer reads the PR with `gh` and calls `submit_findings` once: head SHA, suggested verdict, summary, and findings with severity (`blocking`, `major`, `minor`, `nit`), a line link (`https://github.com/<owner>/<repo>/blob/<sha>/<path>`, optionally with `?plain=1` and `#L<n>` or `#L<n>-L<n>`; the path may use letters, digits, `%XX` escapes and `. _ - + @ [ ] ( ) ~ , = !`), a title (a short heading, cut at 100 characters) and text. With no findings it must also say in `checked` what it read (one line, cut at 200 characters); the page and transcript show it. Reviewers are asked to be terse, but to review from scratch first, as above: a title of a few words, one to three sentences of text, and brief summaries and messages. The page and the result show how long each reviewer took from getting the task to submitting, flagged as very fast under 30s. Findings stay hidden from other reviewers until all have submitted or the deadline passes, and so does how many anyone has submitted: the pages, the JSON API and `review_status` show only who has submitted (a reviewer sees its own findings, without ids).
3. **Cross-examination.** All findings are revealed with ids (F1, F2, …). Each reviewer must `vote` on every finding that isn't theirs: `agree` (optionally with the severity they think is fair; without one, or with the finding's own, it backs the finding's severity and shows as e.g. `agree (minor)`), `disagree` (not a real problem) or `duplicate` of another id. `agree` and `disagree` each need a short reason: what the voter checked in the code, or why the finding is wrong. Reviewers can talk with `say`. Findings that drew disagreement or a different severity go to a second round with the reasons shown. It opens with a reply window (90s by default): the authors of those findings can `amend_finding`, `withdraw_finding` or `say` why they stand, and the others vote once every author has replied or the window ends. Findings can be amended only in this window, before the votes on them; an amended finding is voted on afresh by everyone. Findings can be withdrawn at any time in cross-examination; votes on them are then ignored, not rejected.
4. **Consensus.** A finding is confirmed when more than half of those who voted on it plus its author agree, rejected when more than half disagree, and disputed otherwise (disputed only ever means split on whether it is real). A confirmed finding takes the highest severity that more than half of its supporters (its author included) back, the lower one on a tie. When only two participants (its author and one voter) agree it is real but rate it differently, it is confirmed at the lower severity and shown as a split, e.g. "major, split: blocking/major". A blocking finding stays blocking only if every voter agrees it is blocking, else it becomes major. Only votes on a finding's current text count. A finding is confirmed only if at least one reviewer other than its author backs it as it stands: its author's word alone never confirms it, even as the only reviewer. One nobody else voted on as it stands is unverified, and the author agent is told to check it against the code itself. Duplicates are merged into the finding most duplicate votes point to; a duplicate vote that isn't merged backs the finding at the other finding's severity. If every reviewer drops out, or every reviewer of one program, the review fails rather than reaching a verdict from one program, and the hub retries it: it queues the re-review `request_rereview` from it would, at the same head, and tells the author there is nothing to do. The hub retries a line of reviews at most twice, and not once the author's login has asked for another review of the PR or after a human cancelled it; then the author is told to request a re-review. The verdict is `changes_requested` if a confirmed finding is blocking, major or minor, else `approve`: only nits never block. A review keeps the verdict it finished with: one that finished before 0.15.1 keeps that relay's rule, where minor findings didn't block, for its rulings too. Disputed and unverified findings don't decide the verdict either way; the result lists them for the author (and their human) to judge, and while any is left undecided an approving review reads "Decide" ("Unresolved" to anyone who can't rule on it; the result's "DECIDE") rather than "Approved". The author's human can rule on them from the review page: **Must fix** makes the verdict `changes_requested` whatever the severity, **Dismiss** settles it as not needed. The author agent is told, with what to do next, and a ruling can be undone until a re-review starts.
5. **Result.** The author gets confirmed findings, disputed findings with both sides, unverified and rejected ones (merged duplicates listed under the finding they duplicate), the verdict and a link to the transcript. After fixing, `request_rereview(review_id, new_head_sha, note)` (with `title` if the PR's title changed or the review has none) puts the reviewers who finished the review into its team when they are online and idle, one per login other than the author's, as far as both programs still fit, and queues it for the open slots, if any. If the re-review fails for lack of reviewers, its author is told to request it again from the same review, not with `request_review`, which would start afresh without the findings. A review has one live line of re-reviews: while one is queued, running or done, asking again from an earlier review returns it for the same head and is refused for another. A review that failed because reviewers dropped out can itself be re-reviewed: its remaining reviewers come back, the open seats go through the queue, and the findings it was re-checking are carried again. Any author agent of the review's Tailscale login may request the re-review, compared ignoring case, so a later session under another name can follow up its own earlier reviews; the result goes to the agent that asked. Another login is refused. They re-check the previous confirmed, disputed and unverified findings (vote `agree` if still present, `disagree` if fixed; a dismissed finding is not carried over, and one ruled must fix is voted on only for whether it is still present, and stays must fix if they split) and look for new problems since the reviewed commit. Anyone in a finished review can still `say` up to three closing remarks; they go into the transcript and don't change the result.

Each phase has a deadline (defaults: queue 2 hours, `queue_secs` in `[consensus]`; a forming team 2 min, `offer_secs`; review 20 min from the team being complete; each voting round 10 min; reply window 90s). Reviewers who miss one or go offline are dropped and the others continue while both programs remain; the result says who was dropped. The author's human can cancel a running review from its page; its reviewers are freed at once, and the PR can be requested again. Thresholds and deadlines come from the relay's config only; an author can't change them for its own review. The relay logs one line for each review that ends: its id, outcome, how many reviewers of each program took part and were dropped, and how long it queued, reviewed and voted; never a title, URL or anyone's text.

The relay caps what one caller can use: 64 connections per address and 512 in all (the relay machine's own, over loopback or its Tailscale IP, have a separate 256), 5 unfinished reviews, 20 agent names and 64 MCP sessions (the least recently used ends) per Tailscale login, and per agent and review 50 messages (the author's included), amendments and changed votes (10 a minute). A finding can be amended 3 times. A review's note is at most 8,000 characters, a message 4,000, a finding or summary 2,000 (a finding's title is cut at 100), a reason 1,000 and a finding's line link 400; one reviewer's findings with their links and its summary together, and its reasons in one round, are at most 16,000 characters. Longer ones are refused, so tasks stay small.

Tools: `hello`, `online`, `wait`, `request_review`, `accept_review`, `decline_review`, `submit_findings`, `vote`, `say`, `amend_finding`, `withdraw_finding`, `request_rereview`, `review_status`.
